# CR-01 — تعارض تصمیم نهایی و مرز گردش درخواست

تاریخ 2026-11-08. منشأ: تکلیف کاربر برای استفاده از چارچوب، بازبینی کد و رفتار فعلی؛ این Change Request از طرف استاد در جلسهٔ نهایی ابلاغ نشده است. وضعیت فنی: اجرا و آزموده؛ پذیرش انسانی باز.

## مسئله و فرضیه

route قدیمی تصمیم، HTTP، SQL، چرخهٔ state و audit را کنار هم داشت. تصمیم مخالف روی رکورد نهایی 303 می‌داد؛ درخواست جدید انجام نمی‌شد اما جواب موفق تعارض را مشخص نمی‌کرد. hypothesis: قرارداد 409 و مرز داخلیِ مستقل، این رفتار را روشن و قواعد را جدا آزمون‌پذیر می‌کند.

## تحلیل اثر پیش از اصلاح

Schema/مهاجرت DB، نشست/ورود، فرمول حقوق، سایر فرم‌ها و توپولوژی استقرار از این تغییر اثر مستقیم ندارند. اثر مهم قابل مشاهده برای caller همان HTTP 409 به‌جای 303 است. route قدیمی نیز تصمیم متناقض را overwrite نمی‌کرد؛ ادعای خرابی داده نداریم.

## اجرا و شواهد

مبنای پیش از framework در commit 326f77bb0c3808f7d2db65c1b0a49d27c2cf3959 و snapshot baseline-before-framework-20261108 حفظ شده است. قرارداد/آزمون قبل کد: 16/17؛ تنها failure TC-02-05، actual 303 vs expected 409. بعد تغییر: 17/17، 10 قواعد مستقل و 2 کنترل مرز، سپس 98 assertion رگرسیون.

TRF-02 ادامهٔ محدود همین مرز است: clock سرویس از hr_models به standard library منتقل شد، بدون تغییر قرارداد یا DB؛ پس از آن 29/29 و coverage 96.6٪ در package تصمیم ثبت شد. اجرای شکستِ پیش از این اصلاح کوچک نداریم.

## پیامد و بازگشت

Service قواعد وضعیت را از HTTP و SQL مستقیم جدا می‌کند؛ یک PostgreSQL و lock order request سپس employee باقی است. domain بدون framework آزمون می‌شود. همهٔ HRMS Modular Monolith نشده و این تغییر مسئلهٔ load را حل نکرده است.

چون migration وجود ندارد، بازگشت کد با baseline/source diff ممکن است؛ دادهٔ production reset نمی‌شود. بازگشت به route قبلی، همان پاسخ مبهم 303 را بازمی‌گرداند. restore یا پاک‌سازی دادهٔ واقعی بخشی از این CR نیست.

Review انسانی باید روشن کند که 409 و منع تغییر تصمیم نهایی مطابق سیاست HR است. بازکردن تصمیم یا ایجاد cancel یک تغییر جدید با spec/مدل/آزمون خواهد بود.
