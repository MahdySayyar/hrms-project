# ADR-15 — آزمایش چهار وب برای ورود هم‌زمان

2026-11-17؛ طرح پیش از کد این گام؛ درخواست مستقیم کاربر افزایش تعداد سرورها برای 500 تلاش ورود هم‌زمان است. review انسانی و Gate بازند.

شاهد مبنا: [آزمون تک‌وب Docker](../../08-testing/evidence/login500-before-20261117-a.json)، 500 فرم مستقل، dispatch در 266ms، 500/500 ورود با audit یکتا، P95 ورود 86844ms، 43/52 probe ناموفق با timeout دو ثانیه؛ restart صفر. پاسخ 500 صفحهٔ پس از ورود موفق ولی P95=7468ms بود. پردازه زنده ماند اما سایت هنگام ورود پاسخ‌گو نبود. این آزمون، mixed NFR نیست.

تصمیم آزمایشی: چهار کانتینر وب با همان کد و PostgreSQL در یک project و schema مستقل؛ proxy async موجود با تقسیم round-robin اولین درخواست و affinity مرورگر بازاستفاده می‌شود. فقط hostnameهای صریح `web`, `web2`..`web8` روی HTTP:8000 در حالت Compose مجاز می‌شوند؛ native localhost پیش‌فرض حفظ می‌شود. timeout آزمایش proxy تا 180s صریح و bounded است، زیرا PBKDF2 صحیح فعلی برای جمعیت کامل بیشتر از 30s زمان خواست؛ افزایش timeout به‌تنهایی بهبود ظرفیت تلقی نمی‌شود. خود hash ضعیف، حذف یا cache نمی‌شود.

اولین وب fixture را یک بار در schema تازه می‌سازد؛ سه وب دیگر پس از healthy شدن اول، فقط Uvicorn را در همان schema اجرا می‌کنند. هر وب 8 thread و حداکثر 10 اتصال DB؛ مجموع 40 از max_connections=100 نمونهٔ DB مستقل است. هر مرورگر به همان worker ورود و نشست هدایت می‌شود. backendها پورت میزبان ندارند؛ proxy فقط loopback را منتشر می‌کند. رمزهای تازه در محل ساخته می‌شوند.

اثر FR-01 و BR-01/02: اعتبار حساب/PBKDF2، CSRF، audit پیش از rotation و 401/403 محفوظ‌اند. UC-01 در حالت Compose با همان opaque cookie/CSRF و affinity اجرا می‌شود. طرح عملیاتی D-01 و مدل [چهار وب](../../../models/design/compose-login-replicas.mmd) این topology را پیش از کد ثبت می‌کنند. این مرز Domain/Service/Repository جدید نیست.

ابتدا چهار وب با منطق ورود قبلی آزمون می‌شوند. اگر probe شکست بخورد، طراحی جدا برای محدودکردن کار CPU ورود و آزادکردن اتصال DB پیش از hash، پیش از اصلاح برنامه نوشته خواهد شد. استقرار اصلی تا موفقیت آزمون همان یک وب باقی می‌ماند. افزایش تعداد کانتینر روی همین سخت‌افزار CPU فیزیکی تازه ایجاد نمی‌کند؛ تقسیم درخواست و پاسخ‌گویی را باید اندازه گرفت. خرابی worker نشست همان مرورگر را از بین می‌برد؛ HA، Redis یا stateless بودن ادعا نمی‌شود.

پذیرش: 500 حساب با 500 cookie/CSRF، barrier ورود، توزیع هر چهار worker، 500 پاسخ 303، 500 نشست معتبر، audit یکتا، probeهای /health و داشبورد ناظر بدون failure و restart صفر. زمان ورود جدا و صریح گزارش می‌شود؛ ادعای ظرفیت روی سخت‌افزار دیگر نیازمند آزمون خودش است. منفی/مرز proxy و core/coverage/engineering/Mermaid/pip تکرار می‌شوند.

طرح پیش از کد بستهٔ قابل دانلود: در صورت موفقیت آزمایش ADR-16/17، فایل مستقل compose.capacity.yaml با همان نام project، DB و volume موجود، چهار وب و proxy منتشر می‌شود. وب اول seed معمول را اجرا می‌کند؛ وب‌های بعدی با flag صریح --web-only و پس از healthy شدن وب اول، seed نمی‌کنند. launcherهای قبلی به‌صورت پیش‌فرض چهار وب و با گزینهٔ 1 baseline قدیمی را اجرا می‌کنند. رمزها/volume موجود حفظ می‌شوند؛ fresh-copy startup و تست worker-only پیش از فعال‌کردن deployment اصلی لازم‌اند. تغییر فایل Compose و restart نشست‌ها را از بین می‌برد؛ هیچ انتقال خودکار داده یا migration تازه انجام نمی‌شود.
