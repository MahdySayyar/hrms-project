# ADR-14 — اجرای نسخهٔ دانلودشده فقط با Docker

2026-11-17؛ درخواست مستقیم کاربر برای انتشار عمومی در GitHub و همگام‌کردن تغییرات بعدی. وضعیت: طرح پیش از کد این گام؛ بازبینی انسانی و Gate باز است. Compose و secret initializer موجود از پیاده‌سازی ADR-10 بازسازی و بررسی شدند.

مشکل مشاهده‌شده: راهنمای Docker برای ساخت secret به `.venv/Scripts/python.exe` وابسته بود؛ این محیط در Git نیست و دریافت ZIP روی رایانهٔ تازه برای اجرای Docker کافی نبود.

تصمیم: سرویس موقت `init-secrets` در profile ابزارها همان initializer موجود را با Python داخل کانتینر اجرا می‌کند. فقط اسکریپت initializer به‌صورت read-only و پوشهٔ اختصاصی secret به آن mount می‌شوند؛ شبکه ندارد و پس از اجرا حذف می‌شود. launcherهای PowerShell و Bash اول initializer و سپس دو سرویس موجود را با `--build --wait` اجرا می‌کنند. launcher ویندوز از مسیر خودش کار می‌کند. نصب Python/Git برای مصرف‌کنندهٔ ZIP لازم نیست؛ Docker Desktop با Linux containers یا Docker Engine و Compose v2 لازم است.

اثر FR/BR و UC: قواعد HR، FR-01 و BRهای ورود، UC-01، API و schema تغییر ندارند. تنها پیش‌شرط راه‌اندازی نسخهٔ دانلودشده ساده می‌شود. UC عملیاتی: دریافت ZIP و استخراج، اجرای launcher، تولید رمزهای تازه در محل، آماده‌شدن DB و یک وب، ورود به localhost:8001 با hradmin و رمز محلی. نبود Docker یا خطای daemon/build باید launcher را ناموفق متوقف کند؛ اجرای دوباره secret/volume موجود را حفظ می‌کند.

طراحی: [Compose](../../../deployments/compose.yaml)، [مدل استقرار](../../../models/design/docker-compose.mmd) و D-01 به سرویس موقت اشاره می‌کنند. برنامه همچنان یک پردازهٔ وب دارد و نشست حافظه‌ای است؛ این تغییر شاهد ظرفیت یا HA نیست. تاریخ میلادی و حقوق آموزشی محفوظ‌اند.

انتشار: فایل‌های runtime، `.env`، backup و دادهٔ واقعی وارد Git نمی‌شوند. محتوای قابل انتشار و تاریخچه پیش از push بررسی می‌شوند. تغییرات نهایی مجاز با author عامل commit و به همان remote ارسال می‌شوند؛ هیچ watcher خودکار برای ارسال فایل‌های در حال ویرایش ساخته نمی‌شود. CI آزمون‌های PostgreSQL و راه‌اندازی Docker را روی push تکرار می‌کند.

معیار بررسی: کپی تازه بدون `.env/.venv/.runtime`، تولید دو secret غیرخالی، عدم تغییر secret در تکرار، هر دو سرویس healthy، ورود صحیح/غلط و CSRF، حفظ volume پس از restart، core/coverage/pip و کنترل مهندسی و parser نمودار. فقط schema و دادهٔ ساختگی در آزمون استفاده می‌شود؛ evidence با نام تازه تهیه خواهد شد.

اصلاح طرح پیش از کد دوم همین گام: آزمون نصب روی 8001 به اشغال پورت برخورد کرد و launcher ناموفق متوقف و منابع آزمون پاک شدند. متغیر اختیاری `HRMS_HTTP_PORT` با پیش‌فرض قبلی 8001 برای binding و نشانی خروجی launcher افزوده می‌شود؛ verifier پورت آزاد localhost را برای project یکتای خودش انتخاب می‌کند. اصل پروژه/volume موجود متوقف نمی‌شود.
