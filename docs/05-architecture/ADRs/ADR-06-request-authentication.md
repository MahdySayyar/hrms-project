# ADR-06 — احراز هویت یک بار در هر درخواست و خروج SQL از event loop

2026-11-12؛ تحلیل پیش از کد، در محدودهٔ CR-02؛ پذیرش انسانی باز.

پس از صفحه‌بندی، 50 کاربر بدون خطا ولی با P95=1379ms پاسخ گرفتند. بررسی کد نشان می‌دهد require_login در dependency، require_hr، query_for و config_for یک درخواست دوباره Admin را از پایگاه می‌خواند. همچنین protected_form و browser_form در تابع async، SQL همگام اجرا می‌کنند. این دو هزینه فرضیهٔ گلوگاه بعدی‌اند؛ اثر عملکرد باید با بار دوباره سنجیده شود.

طرح: نتیجهٔ موفق require_login فقط در request.state و با همان شیء نشست نگه داشته شود؛ هر HTTP request تازه همچنان حساب فعال را از PostgreSQL بررسی کند. نشست باطل/منقضی همیشه پیش از استفاده از این نتیجه بررسی می‌شود. dependencyهای async، require_login را در thread pool موجود Starlette اجرا می‌کنند. هیچ cache بین درخواست‌ها و هیچ اعتماد تازه به کوکی ایجاد نمی‌شود؛ تک‌پردازه و نقش/محدوده باقی می‌مانند.

اثر FR-03، BR-01/04، UC-01، D-01 و NFR-M/Response: آزمون شمارش SELECT حساب در یک HTTP request، غیرفعال‌سازی بین درخواست‌ها، انقضا/خروج، نقش/scope و core. بازگشت تنها کد security و dependencyهاست؛ schema تغییر نمی‌کند.

اجرای exploratory 500 کاربر پس از صفحه‌بندی فقط 203 نشست را در 240s آماده کرد و steady آغاز نشد. این شکست setup به‌عنوان ظرفیت workload گزارش نمی‌شود؛ فشار PBKDF2 ورود جدا از بار کاربران واردشده است. ramp محافظه‌کارانه برای ساخت واقعی 500 نشست استفاده و زمان/خطاهای setup مستقل گزارش می‌شود.
