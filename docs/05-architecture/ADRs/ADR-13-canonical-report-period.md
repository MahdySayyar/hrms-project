# ADR-13 — کلید یکسان ماه در گزارش

تاریخ 2026-11-17؛ طرح پیش از اصلاح کد همین گام، بازبینی انسانی در انتظار. قواعد دورهٔ موجود از کد بازسازی شده‌اند؛ قانون حقوق یا تقویم جدیدی فرض نشده است.

## مسئله و شاهد

در `modules.reports` اعتبارسنجی ماه و start/end از `normalized(period)` استفاده می‌کنند، اما query جمع فیش `Payslip.period == period` از متن اولیه استفاده می‌کند. بنابراین ماه معتبر با ارقام فارسی/عربی، تردد درست و جمع فیش صفر می‌دهد، چون کلید ذخیره‌شده `YYYY-MM` با ارقام ASCII است. این رفتار با فیش‌های ساختگیِ ماه 2025-01 پیش از اصلاح بررسی می‌شود.

## تصمیم و قرارداد

پس از اعمال پیش‌فرض موجود برای ورودی خالی، `period` فقط یک‌بار normalize شود و برای validation، start/end، query و context همان مقدار استفاده شود. ورودی‌های `2025-01`، `۲۰۲۵-۰۱`، `٢٠٢٥-٠١` و نسخهٔ دارای فاصلهٔ پیرامونی همان ماه میلادی را برگردانند. ماه نامعتبر همچنان 400 است؛ ورودی whitespace-only همچنان 400 و مقدار خالی همان ماه جاری است.

FR-22 و BR-13 به استفاده از کلید استاندارد دوره و اتصال به snapshotهای موجود تصریح می‌کنند. نقش/محدوده و نمایش جمع حقوق فقط admin حفظ می‌شوند. هیچ تبدیل جلالی، تغییر محاسبه یا بازنویسی فیش رخ نمی‌دهد.

## اثر و بازگشت

اصلاح محدود در `app/modules.py`، UC-11 و آزمون‌های گزارش؛ schema، API route، نوع پاسخ و استقرار ثابت‌اند. مهاجرت داده لازم نیست، چون calculator از قبل کلید ASCII می‌سازد. بازگشت حذف normalization تازه است و ناسازگاری قبلی را برمی‌گرداند. اثر قبل/بعد در گزارش مستقل ثبت می‌شود؛ پذیرش انسانی در انتظار است.
