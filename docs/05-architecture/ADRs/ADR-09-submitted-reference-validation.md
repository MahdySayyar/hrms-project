# ADR-09 — اعتبارسنجی محدود مرجع فرم ارسالی

2026-11-15؛ تحلیل پیش از کد؛ review انسانی باز. کاربر هدف را مجدداً معماری بدون خطا برای ورود هم‌زمان 500 نفر تأکید کرد.

مشکل واقعی: پس از transport، steady 500 نفر فقط یک failure در 5144 درخواست داشت، ولی burst مرخصی تنها 403/500 پاسخ و ذخیره/audit قابل‌تأیید داشت. بازبینی مسیر `save_record -> fields_for -> options_for` نشان داد برای اعتبارسنجی employee_id یک POST معتبر، تمام 10,000 Employee بارگذاری و نام همه ساخته می‌شود؛ 500 POST هزینهٔ حدود پنج میلیون پرونده را تکرار می‌کند. این یک مشاهدهٔ کد در کنار failure آزمایش است؛ عدد زمان منتسب به آن هنوز اندازه‌گیری نشده است.

انتخاب: فقط هنگام save_record، گزینهٔ هر مرجع source با شناسهٔ ارسال‌شده و همان query scope/شرط eligibility خوانده شود. ورودی خالی/نامعتبر query محدود بدون نتیجه دارد؛ انتخاب خارج scope یا حذف‌شده همچنان 400 همان فرم است. مقدار نهایی و قواعد دامنه با validate_record و FK دوباره بررسی می‌شوند. choices ثابت مانند نوع مرخصی همان قبلی‌اند. برای نمایش GET و فرم خطا هنوز گزینه‌های کامل استفاده می‌شوند؛ محدودکردن نمایش این گزینه‌ها تغییر UI مستقلی است و در این تصمیم انجام نمی‌شود.

اثر: FR-12، BR-04/BR-07/BR-14، UC-02، D-04 و helper مشترک source در سایر ماژول‌ها. schema/نرخ/چرخهٔ تصمیم تغییر ندارند. محدودیت منابع، پاسخ عمومی، atomic audit و کنترل نقش/CSRF محفوظ‌اند. این helper مرز دامنهٔ جدید نیست.

پذیرش: آزمون PostgreSQL مثبت مرخصی/سایر sourceها، شناسهٔ خارج scope/حذف‌شده/غیردیجیتال، شناسهٔ فارسی و optional خالی، و مشاهدهٔ اینکه اعتبارسنجی موفق فهرست کل Employee را hydrate نمی‌کند. اجرای core و رگرسیون هشت حوزه، سپس 500 کاربر و burst 500 مرخصی با بررسی مستقل ذخیره/audit. هدف بدون خطای کاربر و NFR قدیمی سرعت جدا گزارش می‌شوند؛ هیچ موفقیتی پیش از اجرا فرض نمی‌شود.

بازگشت: capture کد قبل از اجرای ظرفیت محفوظ است و می‌توان helper را به رفتار قبلی بازگرداند. دادهٔ واقعی تغییر نمی‌کند؛ آزمایش فقط schema disposable و پروندهٔ ساختگی دارد.
