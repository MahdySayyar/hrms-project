# EXP-REQUEST-AUTH — شاهد مستقل احراز هویت در هر درخواست

گزارش در 2026-11-15 از اصلاح و شواهد 2026-11-12؛ پذیرش انسانی باز. ADR-06 و D-01 پیش از کد ثبت شدند؛ جزئیات UC در همان چت بلافاصله پس از اصلاح تکمیل شدند و این گزارش نتیجه پس از اجرا نوشته شده است.

مشکل: خواندن چندبارهٔ همان حساب در یک HTTP request و SQL همگام داخل dependency فرم async. اصلاح: خواندن فعال‌بودن حساب یک بار در هر request، استفادهٔ محدود از request.state برای همان نشست معتبر و انتقال SQL dependency به thread pool. cache بین requestها اضافه نشده؛ غیرفعال‌سازی حساب در request بعد اعمال می‌شود.

| اجرای 50 کاربر، حدود 30s steady | درخواست | خطا | P95 |
|---|---:|---:|---:|
| [صفحه‌بندی](../../08-testing/evidence/capacity-pagination-50-20261112-a.json) | 1743 | 0 | 1379ms |
| [صفحه‌بندی + auth](../../08-testing/evidence/capacity-auth-50-20261112-a.json) | 2169 | 0 | 1250ms |

[اجرای 500 نفر](../../08-testing/evidence/capacity-auth-500-20261112-a.json) با نرخ ورود کنترل‌شده به 500 نشست رسید، اما در 30.2s steady از 4077 درخواست، 2524 خطا و P95=11498ms داشت. تغییر نرخ setup برای رسیدن به جمعیت کامل صریح است؛ ورود تدریجی با ورود یک‌بارهٔ 500 نفر برابر نیست. این اصلاح به‌تنهایی هدف ظرفیت را برآورده نکرد.

TC-01-04 شمار SELECT حساب در GET/POST و غیرفعال‌سازی قبل از request بعد را با PostgreSQL واقعی می‌سنجد. آزمون‌های نقش، scope، CSRF، انقضا و login در [مجموعهٔ جاری](../../08-testing/evidence/core-final-20261115-a.json) هستند. قواعد رمز/نشست، schema و سایت تک‌پردازه محفوظ‌اند.
