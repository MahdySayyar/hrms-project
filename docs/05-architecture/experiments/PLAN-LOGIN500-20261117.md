# برنامهٔ آزمون ورود هم‌زمان ۵۰۰ کاربر

2026-11-17؛ درخواست مستقیم کاربر: هنگام ورود هم‌زمان ۵۰۰ نفر پروژه از دسترس خارج نشود. این برنامه پیش از ابزار و اصلاح تازه نوشته شده است. رفتار ورود و Compose موجود بازسازی از کد است؛ review انسانی و Gate بازند.

مبنای فعلی یک وب Docker و PostgreSQL است. نشست‌ها در حافظهٔ همان وب‌اند. آزمون تاریخی چهار وب، ورود تدریجی داشت و پذیرش ورود هم‌زمان Docker نیست. در route ورود فعلی، SELECT حساب، PBKDF2 با 600000 iteration و audit/commit داخل همان Session هستند؛ thread عمومی و اتصال DB هنگام پردازش CPU نگه داشته می‌شوند. این مشاهده فرضیهٔ گلوگاه است؛ نتیجهٔ فشار هنوز اندازه‌گیری نشده است.

ابزار تازه از کپی کد بدون `.env`/runtime native یک project Compose و schema PostgreSQL یکتا ایجاد می‌کند. 10000 پرونده و 500 حساب HR ساختگی با یک رمز تصادفی مخصوص آزمایش ساخته می‌شوند؛ استفاده از hash مشترک در fixture هزینهٔ ساخت داده را کم می‌کند، ولی هر درخواست ورود واقعاً PBKDF2 را اجرا می‌کند. حساب ناظر جدا است. همهٔ 500 فرم/کوکی/CSRF قبل از barrier آماده می‌شوند؛ سپس ورودها هم‌زمان dispatch می‌شوند. /health و داشبورد ناظر هر 200ms در این پنجره با timeout دو ثانیه بررسی می‌شوند.

کاربر در ادامه تصریح کرد مسئله فقط 500 تلاش ورود در یک لحظه است. پس از احراز هویت، 500 نشست جدا و audit همان 500 حساب کنترل می‌شوند. آزمون ترکیبی پنج‌دقیقه‌ای و burst مرخصی خارج از این درخواست‌اند و NFR-01 از آزمون ورود تأیید نمی‌شود. worker/DB، CPU/RAM میزبان/generator و زمان dispatch/ورود/probe ثبت می‌شوند؛ منابع آزمایش در پایان حذف و raw/evidence با نام تازه حفظ می‌شوند.

مبنای رفتار FR-01، BR-01/02 و UC-01 تغییر نکرده است. پس از مشاهدهٔ شکست واقعی، طرح اصلاح شامل قرارداد FR/BR، UC، مدل و ADR پیش از کد نوشته خواهد شد. پیش از داشتن شاهد، replica، Redis، gateway یا تغییر topology استقرار اصلی اضافه نمی‌شود. تاریخ میلادی، حقوق آموزشی و محدودیت نشست حافظه‌ای محفوظ‌اند.

بازنگری ابزار پس از اجرای چهار وب b: 500 ورود/نشست موفق و 867/868 probe موفق بود؛ یک probe فقط در 407ms با exception سمت client ثبت شد، نه timeout کامل دو ثانیه. class خطای client قبلاً ثبت نمی‌شد. connector مولد هم اتصال idle را بازاستفاده می‌کرد؛ در تکرار بعدی اتصال تازه برای هر درخواست و ثبت class خطا انتخاب می‌شود تا failure کلاینت به سرور نسبت داده نشود. workload، تعداد حساب، قدرت hash و deadlineهای صریح ثابت می‌مانند. identity هر نشست با display name یکتای ساختگی و تعداد cookieهای یکتا کنترل و خود ابزار نیز snapshot/hash می‌شود؛ هیچ مقدار cookie یا password منتشر نمی‌شود.
